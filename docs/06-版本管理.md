# LinkNest — 版本管理规定

> 本规定自 V1.1 起生效。M0～M3C 仅作为 V1.0 的历史阶段编号保留，不再用于规划新功能。

- 状态：已确认
- 生效日期：2026-09-20

## 1. 版本号

版本号采用 `主版本.次版本.修订版本`：

- **主版本**：出现不兼容的产品定位、数据或协议变化时递增，例如 `2.0.0`。
- **次版本**：增加一组向后兼容的新功能时递增，例如历史空间使用 `1.1.0`。
- **修订版本**：只包含兼容的问题修复和小幅优化，例如 `1.1.1`。
- Flutter 构建号使用 `版本号+递增数字`，例如 `1.1.0+12`；每次对外生成安装包时构建号必须递增。
- Git 发布标签使用 `v主版本.次版本.修订版本`，例如 `v1.1.0`。

## 2. 迭代状态

每个版本依次使用：`规划中 → 开发中 → 验收中 → 待发布 → 已发布`。暂停的版本明确标记为“暂停”，不得把已规划或代码完成写成已发布。

当前状态：

- `1.0.0`～`1.2.0`：开发里程碑，未作为稳定版发布；对应需求和验证历史保留在需求文档与变更日志中。
- `1.3.0`：2026-10-18 首个稳定版；Android 安装包版本 `1.3.0+3`，直接分发的 APK 为 `LinkNest_1.3.apk`。代码依次从 `feature/1.3.0` 合并至 `develop`、`main`，发布标签为 `v1.3.0`。iOS App Store 发布仍需独立完成签名与分发。
- `1.4.0`：2026-11-09 发布；Android 安装包版本 `1.4.0+4`，直接分发的 APK 为 `LinkNest_1.4.apk`，发布标签为 `v1.4.0`。包含 App 内隐私政策入口；Windows 环境未执行 iOS 构建，iOS 真机展示待验证。

## 3. 文档与分支

- 用户可以先在 [02-需求文档.md](./02-需求文档.md) 的对应版本中填写重大功能或逻辑需求；开发前再分配 ID，并按功能模块和依赖整理。
- 同一需求的补充、同一功能中的连续 Bug 或同一根因的修复沿用已有 ID，不重复创建需求。
- 需求完成后仍保留在需求文档中，只更新状态、技术概括、验收标准、变更原因和验证记录。[03-变更日志.md](./03-变更日志.md) 按相同版本使用同一需求 ID。
- 影响核心功能的历史 Bug 在当前开发版本中创建或沿用“修复”需求；细节修复无需单独需求。
- 正式发布时，为变更日志中的对应版本补充发布日期，并创建 Git 标签。
- 重大产品边界变化先更新 [01-产品概述.md](./01-产品概述.md)；需求、技术方案或验收变化先更新 [02-需求文档.md](./02-需求文档.md)，再修改代码。细节调整不逐项记入需求和变更日志。
- 开发分支按版本和功能组命名，例如 `feature/1.1.0-history-spaces`；只有准备发布时才建立 `release/<版本号>` 分支。不再创建新的 `M*` 功能分支。
